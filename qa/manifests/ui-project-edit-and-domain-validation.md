## What changed
- `src/autotester/ui/helpers.py` — new `_require_reachable_base_url(base_url, domains)`.
  Refuses a project whose own `base_url` host is not covered by its `allowed_domains`, and a
  `base_url` the browser could not open at all (`host_of` returns empty). Composed from the
  two functions that already own this question — `browser.secrets.host_of` and
  `Project.allows_domain` — so the check can never be stricter or looser than the boundary it
  guards (subdomains keep working, because `allows_domain` already accepts them). Lives in
  `helpers.py` because that module's stated job is shared request-validation for every route.
- `src/autotester/ui/app.py::onboard_submit` — calls it before persisting, so an unrunnable
  project is refused at the moment the mistake is made instead of hours later mid-run.
- `src/autotester/ui/routes_project_edit.py` (new, 78 lines) —
  `GET/POST /projects/{slug}/edit` for the three fields a human can get wrong at onboarding:
  name, base_url, allowed_domains. Runs the same validator, so editing is not a back door
  around the onboarding check. The **slug is deliberately not editable**: it names the
  directory every run, case, rubric and browser profile is already filed under, so renaming it
  would orphan all of them.
- `src/autotester/ui/app.py` — registers the router; the project page gains a
  `⚙ Project settings` action.
- `docs/MAP.md` — regenerated by `autotester map` (new module).
- `tests/test_ui_project_edit.py` (new) — 10 tests: onboarding refuses domains excluding the
  project's own base_url (the literal `all` incident) and writes nothing; the error names the
  host to add; a non-openable base_url is refused; a **subdomain of an allowed domain still
  onboards** (the validator must not over-tighten); the edit form shows current values;
  editing persists through the store and leaves the slug alone; editing refuses stranding
  domains and an empty domain list, with the on-disk value verified unchanged in both; unknown
  project is 404; the project page links to its settings.

## How it was found
Umesh onboarded the ERP project through the UI and typed `all` in Allowed domains, plainly
meaning "allow everything". It was stored verbatim as a literal domain named `all`, so
`projects/erp/project.json` held `allowed_domains: ['all']` against
`base_url: https://www.vidysea.com/erp`. The project was dead on arrival: the first real run
came back INCONCLUSIVE with
`NavigationRefused: 'https://www.vidysea.com/erp' is outside allowed domains ['all']` — a
failure hours removed from the mistake, phrased in terms the user could not act on, and with
no route anywhere to correct it.

## What this unit deliberately does NOT do
It does **not** teach `allowed_domains` a wildcard. That field is the documented boundary the
browser is never allowed to cross (`CLAUDE.md` credentials section, `ARCHITECTURE.md` security
model); an allow-anything escape hatch is a security-model decision for Umesh, not a
validation fix a maker makes on its own while fixing a usability bug. The edit form says so
where the user would look for it: "There is no wildcard: name every host you mean."
