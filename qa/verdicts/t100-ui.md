## New this cycle: env_editor.py permission hardening (not part of AT-035, judged independently)

`set_env_value` (env_editor.py:14-46) now writes via `os.open(str(env_path), O_WRONLY|O_CREAT|
O_TRUNC, 0o600)` then, in a `finally` block guarded by `contextlib.suppress(OSError)`, an
additional `os.chmod(env_path, 0o600)`. Read the logic carefully: `os.open`'s mode argument only
applies when the file is newly created — if `.env` already existed with wider permissions (e.g.
0o644, inherited from an earlier unprotected write or git checkout), `os.O_CREAT` on an existing
path does not narrow its mode. The defensive `os.chmod` after every write is what actually
guarantees 0o600 in that case, independent of whether the file pre-existed. This is correct
reasoning, not just an incantation — verified by reading the stdlib semantics of `os.open`
myself, not trusting the manifest's explanation.

The property U3 already required (never returns/logs/echoes `value`) is untouched by this change
— `value` still only ever appears in the `new_line` string written to disk.

`test_set_env_value_writes_owner_only_permissions` (test_ui.py:146-153) is correctly marked
`@pytest.mark.skipif(os.name == "nt", reason="POSIX permission bits don't apply on Windows")` —
confirmed this checker's own run shows it in the `s` (skipped) column on this Windows box, for
the stated reason, not silently passing. This is the right test shape: a Windows-only run cannot
prove POSIX permission bits, and the test says so honestly rather than asserting something
Windows can't provide evidence for.

## Security addendum confirmation (post-cycle-2) — 2026-09-03

Scope: two HIGH-severity issues an automated security review found on the same files *after*
the cycle-2 PASS above (not part of AT-035, not re-litigating cycle 2). This section only judges
those two fixes; the cycle-2 PASS above stands on its own merits.

1. **env file injection** — `src/autotester/ui/env_editor.py`: a `.env` value containing a
   newline could inject an arbitrary extra `KEY=VALUE` line.
2. **path traversal via `slug`** — `src/autotester/ui/app.py`: `slug` (and `run_id`) were used
   directly to build a filesystem path with no validation.

### What I checked myself (fresh context, read-only)

- Read `src/autotester/ui/env_editor.py` in full (64 lines). `set_env_value` (line 21-63)
  validates `_KEY_RE.fullmatch(key)` (UPPER_SNAKE_CASE) and `"\n" in value or "\r" in value`
  at lines 36-39, **before** `env_path.read_text()` (line 41) or the `os.open`/write (lines
  55-63) — there is no code path in the function that reads or writes the file before those two
  checks. `InvalidEnvValue(ValueError)` (line 17-18) is a real, distinct exception class, not a
  bare `ValueError` or string. No bypass found.
- Read `src/autotester/ui/app.py` in full (168 lines). `_require_slug` (line 30-33) and
  `_require_safe_id` (line 36-39) are defined once and used everywhere. Grepped `def.*slug`
  myself rather than trusting the manifest:
  - `index()` (58) — no slug param, only reads already-validated on-disk slugs via
    `_project_slugs()`.
  - `onboard_form()` (66) — no slug param.
  - `onboard_submit()` (79-90) — calls `_require_slug(slug)` directly at line 86, **before**
    `Project(...)` is constructed or `ProjectStore(slug).save_project(...)` is called (89) —
    confirmed validation precedes any project directory creation.
  - `project_detail()` (93-105), `env_editor_view()` (108-123), `env_editor_submit()`
    (126-135), `report()` (154-167) — all call `_load_project_or_404(slug)` first, which itself
    calls `_require_slug(slug)` at line 50, before `ProjectStore(slug)` (51) or
    `store.load_project()` (52).
  - `run_view()` (138-151) — calls `_load_project_or_404(slug)` (140, validates slug) and then
    `_require_safe_id(run_id, "run_id")` (141) before `store.load_verdicts(run_id)` /
    `store.load_results(run_id)`.
  - That is every route in the file that takes `slug` or `run_id` — none bypass validation.
  `_require_slug`'s regex (`^[a-z][a-z0-9-]*$`, line 25) is byte-for-byte the same pattern as
  `schema.project.Project.slug`'s own field validator (checked `src/autotester/schema/project.py`
  separately) — no risk of the UI accepting a slug the schema would later reject, or vice versa.
- Wrote my own reproduction (not the manifest's) driving the real HTTP routes via
  `fastapi.testclient.TestClient(app)` against a scratch `AUTOTESTER_ROOT`:
  - `POST /onboard` with `slug="../evil"` → **400**, no directory created outside
    `projects/<slug>/`.
  - `POST /onboard` with `slug="Evil"` (uppercase) → **400**.
  - `POST /onboard` with a null byte embedded in `slug` → **400**.
  - `GET /projects/..%2f..%2fevil` (URL-encoded traversal) → **404** (path-normalized by the
    ASGI router before reaching the handler; no 200/500, no filesystem leak).
  - `GET /projects/UPPER` → **400** (rejected by `_require_slug` inside
    `_load_project_or_404`, not a schema-level 404 masking the real problem).
  - Onboarded a legitimate `demo` project, declared a `DEMO_TOKEN` secret, then:
    - `POST /projects/demo/env` with `value="abc\ndef=INJECTED"` → **400**; read `.env` back —
      byte-for-byte unchanged from before the request; no `INJECTED` line present.
    - Same with `value="abc\rdef=INJECTED2"` → **400**.
    - `POST /projects/demo/env` with a legitimate single-line value → **200**, `.env` now
      contains exactly `DEMO_TOKEN=legit-value`, proving the checks reject bad input without
      breaking the good path.
  - `GET /projects/demo/runs/..%2f..%2fetc` → **404**.
  - All assertions passed on first run; full script output and exit code confirm no bypass.

### Judgment on completeness

- No path in `set_env_value` writes before validating — confirmed by reading control flow, not
  just the presence of the checks.
- Every route taking `slug` goes through `_load_project_or_404` (or, for `onboard_submit`, calls
  `_require_slug` directly before any write) — confirmed by enumerating every `slug`-taking
  function in the file, not by trusting "every route" in the manifest.
- `_require_safe_id` is applied to `run_id` in `run_view`, the only route that takes `run_id`.
- Checked for other gaps beyond the two named issues: `onboard_submit`'s `name`, `base_url`,
  `allowed_domains` form fields are not used to build filesystem paths (only `slug` is), so they
  are out of scope for path-traversal/injection; they pass through `Project(...)` construction,

  fixes. `_require_slug`'s regex allows a one-character slug like `"a"` — this matches
  `Project.slug`'s own pattern exactly (no UI/schema mismatch), so it is not a UI-introduced gap;
  any length-limit concern would be a schema-level decision, out of scope here. No other
  route/parameter in `app.py` builds a filesystem path from unvalidated user input.
